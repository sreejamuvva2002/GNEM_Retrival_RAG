  Codebase Review Summary

  1. Overall Status

  The architecture matches the intended pipeline. Offline builds 1 parent + 5
  children per KB row and writes both to PostgreSQL (parents in parent_chunks,
  children + vectors in child_chunks via pgvector). Runtime executes BM25 +
  dense child retrieval in parallel, merges and dedupes by chunk_id, expands to
  deduped parents via parent_record_id, fetches parent_chunk_text, reranks at
  the parent level with a cross-encoder, and returns the top-k parent chunks to
  the LLM. HybridRetrievalTrace is populated with the expected counts. RRF is
  correctly absent. The current code is correct for the intended task; the main
  risks are dead config, a checked-in .env with live DB credentials, and stale
  test files blocking full pytest.

  2. Runtime Pipeline Review

  What is correct:

  - hybrid_retrieval/orchestrator.py:40-68 — sparse/dense run in parallel
  through _retrieve_children, merger dedupes by chunk_id, parent_mapper returns
  dedup-by-record_id parents, then reranker.rerank_parents is called, and the
  trace records all expected counts.
  - hybrid_retrieval/merger.py:9-26 — stable, order-preserving dedup by
  chunk_id. No accidental RRF.
  - hybrid_retrieval/parent_mapper.py:20-29 — delegates to
  parent_fetcher.fetch_parents, which calls _dedupe first, preserving fetch
  order.
  - retrieval/parent_fetcher.py:21-58 — pulls only record_id, source_row_id,
  parent_chunk_text from parent_chunks, which is exactly what the LLM step
  needs.
  - hybrid_retrieval/reranker.py:60-83 — cross-encoder applied directly on
  parent.parent_chunk_text, returns the top-k parent contexts.
  - hybrid_retrieval/run_rewritten_50.py:139-159 — uses retrieve(...) to feed
  only reranked parent text to the LLM.

  What still needs attention:

  - retrieval/bm25_retriever.py:62-109 opens a brand-new psycopg2.connect and
  loads every child chunk into memory on first request. Fine for ~1k chunks, but
   the loaded corpus and BM25Okapi index are recreated per-process. For
  long-running services consider a single shared connection pool and an explicit
   warm-up step. This is future work, not a correctness bug.
  - retrieval/dense_pgvector_retriever.py:38-44 opens a fresh DB connection on
  every query. Same pooling note.
  - The orchestrator returns parent contexts in reranker score order, but it
  discards the cross-encoder scores. If you ever want to surface them in the
  trace, you'd need to thread a (parent, score) pair through.
  - retrieve_with_sources returns the raw pre-rerank sparse_children /
  dense_children but the workbook writers only show top-N child metadata; the
  per-source totals reflect post-DB-truncation counts (capped at RETRIEVER_TOP_K
   = 250), which is what you want.
  - Two runner files duplicate the same _format_child_contexts
  (run_rewritten_50_retrieval_only.py:161-177 and
  run_rewritten_50_all_modes.py:309-326). Not a bug; just drift risk.

  3. Offline Pipeline Review

  - offline_pipeline/index_pgvector.py:28-82 builds chunks, writes debug XLSX,
  then stores parents and child vectors. Argument parsing is clean.
  - offline_pipeline/chunking/operations.py:20-43 and
  chunking/relationship.py:18-37 produce exactly len(parents) × 5 children with
  stable deterministic chunk_ids of the form <record_id>_<TYPE> — this is what
  the runtime parent mapper relies on.
  - offline_pipeline/postgres_store.py:43-75 issues an INSERT … ON CONFLICT 
  (record_id) DO UPDATE, so re-runs are idempotent.
  - offline_pipeline/pgvector_store.py:97-156 uses the actual model embedding
  dimension and only creates the table if missing; --recreate-child-table is
  correctly opt-in.
  - chunking/parent_chunk.py:111-138 writes parent text by hand-listing every KB
   column. That is the only place all 16 columns are enumerated, so the parent
  chunk format is implicitly bound to the current KB schema.

  Issues / future suggestions (no changes made):

  - relationship.validate_relationships exists and is the right safety net, but
  index_pgvector.py never calls it. Future: run it after
  build_parent_child_chunks and fail-fast on orphans, duplicates, or wrong
  children-per-parent counts.
  - pgvector_store.py:41-45 hardcodes WITH (lists = 100) for the IVF index.
  Acceptable for 1,025 chunks, but for KB growth this should be a config knob
  (e.g. PGVECTOR_IVF_LISTS) derived from row count (rule of thumb: lists ≈ 
  sqrt(N)).
  - parent_chunk.py:152-154 encodes KB_ROW into the record_id. Harmless, but if
  you ever add a non-Excel source you'll want the prefix derived from
  source_type.
  - The parent payload encodes 16 distinct KB columns into SQL DDL
  (postgres_store.py:15-41). Future: if KB columns drift, drive the
  parent_chunks schema from loader.KBColumns so it stays in sync without
  hand-edits.

  The three modes

  1. only_rag — retrieval-grounded, strict

  - What the LLM gets: the user question plus the top-k reranked parent chunks.
  - Instruction: "Use ONLY the provided context. If the answer isn't there, say
  so. Do not guess from general knowledge."
  - Purpose: Tests pure retrieval quality. The LLM is a thin formatter on top of
   retrieved evidence.

  2. only_pretrained — no retrieval, model knowledge only

  - What the LLM gets: the user question and nothing else. No retrieval is run.
  - Instruction: "Answer from what you already know from pre-training. Don't
  invent precise companies/products/numbers if you're unsure."
  - Purpose: Baseline of what the Ollama model knows about the Georgia EV supply
   chain without your KB.
  - Important: No KB data is given. This is question-only.

  your full formatting style guide instead of the minimal one.
