LLM Wiki

An incremental, LLM-powered knowledge graph that transforms raw crawled documents into a structured, searchable, and traceable wiki — one entity at a time.

📁 llm_wiki.py 🦙 Ollama · mistral:latest 📖 Markdown output 🔗 Provenance tracking
Overview

What is LLM Wiki?

📥

Input

JSONL files of raw crawled documents — news articles, web pages, government docs — each linked to a company.

🤖

Processing

A local Ollama LLM reads each document and extracts: entity name, entity type, key facts, and related entities — as structured JSON.

📖

Output

Persistent Markdown wiki pages, one per company/concept, continuously updated as new documents are ingested. Full provenance tracking.

Core Logic

LLM Extraction

For each document, a carefully crafted prompt is sent to Ollama. The LLM must return only valid JSON — no prose.

  • Company hint is labeled as a hint, not a directive — LLM decides the real entity from content
  • Instructions to return "Unknown" for index/magazine/navigation pages
  • Minimum 2 specific, substantive facts required — otherwise page is skipped entirely
  • 3-layer JSON extraction: direct parse → substring parse → fallback skip
# Prompt structure sent to Ollama

Analyze this document...

Document Title: {title}
URL: {url}
Hint: {linked_company}

Content: {body_text[:1500]}

Rules:
- main_entity = PRIMARY subject
- If magazine/directory → "Unknown"
- facts = specific, substantive only
- no emails, URLs in entities

{"main_entity": ..., "facts": [...], ...}
Deduplication

Entity Normalization

Without normalization, the same company generates multiple fragmented pages. A fuzzy-match pipeline prevents this.

# Strip corporate suffixes first
"Duckyang Co.,Ltd." → "duckyang"
"DUCKYANG CO.,LTD." → "duckyang"
"Duckyang Industrial Co." → "duckyang"
"Duckyang Ind." → "duckyang"

# Then fuzzy match with SequenceMatcher
threshold = 0.82
score("duckyang", "duckyang") = 1.00 ✓

# Cluster → pick shortest as canonical
canonical = "Duckyang" # wins

Cluster-based Merging

All near-duplicates are clustered first, then the best canonical title is chosen (shortest normalized name, most sources as tiebreaker).

Real-time Resolution

_find_canonical_entity() runs on every ingest — new docs automatically merge into the right existing page.

Email/URL Guard

Entities containing @ or starting with http are silently dropped before any page creation.

Storage Format

Wiki Page Structure

Each entity is stored as a .md file with embedded JSON frontmatter:

---
{
  "title": "Duckyang",
  "entity_type": "company",
  "last_updated": "2026-06-07T...",
  "sources": ["sha256:abc1..."],
  "related_entities": ["SK Innovation"],
  "fact_sources": {
    "Invests $10M in Georgia": ["sha256:abc1..."]
  }
}
---

# Duckyang

## Overview

## Key Facts

- Hiring 285 people for EV battery parts
- Founded 1990, Seoul, South Korea

📁 kb/wiki/ directory

One .md file per entity, named by safe-filename conversion of the entity title.

🗃️ _index.json

Master lookup for all pages, entity cross-references, and the sources_processed set that prevents duplicate ingestion.

🔗 fact_sources

Per-fact provenance: maps each bullet-point fact to the list of source doc SHA-256 hashes that contributed it.

New Feature

Fact Provenance Tracking

Every fact is now traceable to the exact source document(s) that contributed it — crucial for RAG validation and audit.

# Query provenance at any time
wiki = LLMWiki("kb/wiki")
print(wiki.get_provenance("Volkswagen"))

# Output:
## Provenance: Volkswagen

- Investing $2.1B in Scout Motors plant
  Sources: sha256:abc123ef...

- Plans to hire 4,000 workers by 2026
  Sources: sha256:abc123ef..., sha256:def456...

✓ Corroboration visible

If two documents say the same thing, both source IDs appear — showing the fact is independently corroborated.

✓ Survives deduplication

When duplicate facts are merged, their provenance is combined — no source information is lost.

✓ Survives entity merges

When duplicate entity pages are merged (e.g. "Duckyang Co.,Ltd." → "Duckyang"), all fact_sources are preserved.

Legacy facts

Facts written before provenance was added show "predates provenance tracking" — a clean, honest signal.

API Reference

Key Methods

Method Purpose
ingest_document(doc_id, doc)Main entry point. Calls Ollama, resolves entity, creates/updates wiki page. Returns list of pages updated.
_find_canonical_entity(name)Fuzzy-matches a name against all existing page titles. Returns canonical title if score ≥ 0.82, else None.
merge_duplicates(dry_run)Clusters all near-duplicate page titles, picks canonical, merges content + provenance, deletes orphan files.
get_provenance(title)Returns human-readable report mapping each fact → source doc SHA-256 IDs.
search(query, top_k)Keyword search over page titles and entity types. Returns ranked results with content previews.
export_as_markdown(output)Compiles all wiki pages into one big markdown file, grouped by entity type.

Usage Guide

Running the Wiki

# 1. Activate venv
.\.venv\Scripts\Activate.ps1

# 2. Run ingestion (first 50 docs)
python -m georgia_ev_intelligence.kb_builder.ingest_wiki \
  --source kb/raw_docs/ddg_search.jsonl \
  --limit 50 \
  --wiki-dir kb/wiki

# 3. Export full wiki to one file
python -m ... --export kb/wiki_export.md

# 4. Merge duplicates after a big run
wiki.merge_duplicates()

# 5. Check fact provenance
wiki.get_provenance("Volkswagen")

⚠️ Prerequisites

Ollama must be running locally with mistral:latest pulled. Verify with ollama list.

💡 Recommended workflow

Start with --limit 5 to validate Ollama is working, then increase. The index tracks processed docs safely across runs.

🔁 Idempotent

Re-running with the same source is safe — already-processed doc hashes are skipped via SHA-256 index. Interrupted runs pick up where they left off.
