  Storage: Why Excel Fails Here

  concatenated blob. Excel has a 32,767-char cell limit — 45 parent chunks
  easily blows past that. The right format is JSONL (one JSON record per line
  per question).

  Each record stores exactly what RAGAS needs:
  {
    "question_id": 1,
    "question": "Which companies...",
    "ground_truth": "There are 18...",
    "answer": "Based on the context...",
    "contexts": ["chunk text 1", "chunk text 2", ...],
    "pipeline": "rag_only",
    "model": "qwen2.5:14b",
    "trace": { "sparse_child_count": 5, "dense_child_count": 8, ... }
  }

  ground_truth, answer, and contexts are the exact field names RAGAS expects. No
   transformation needed when you run metrics later.

  ---
  1. answer_accuracy
  Compares the generated answer against the golden/reference answer. Scores how
  correct the answer is.
  - Needs: question + answer + ground_truth
  - Applies to: all 4 pipelines (everyone has a golden answer)

  2. faithfulness
  Checks whether every factual claim in the answer is actually supported by the
  retrieved contexts. Catches hallucinations that aren't grounded in the KB.
  - Needs: question + answer + retrieved_contexts
  - Applies to: rag_only, hybrid_rag, direct_kb — NOT pretrained_only (contexts
  list is empty [])

  3. response_groundedness
  Measures how much of the response is directly traceable to the retrieved
  context. Subtly different from faithfulness — faithfulness asks "did the model
   invent anything?", groundedness asks "how much of the response is anchored in
   the context?"
  - Needs: answer + retrieved_contexts
  - Applies to: rag_only, hybrid_rag, direct_kb — NOT pretrained_only

  ---
  Why pretrained_only only gets 1:
  The other two metrics require retrieved contexts. pretrained_only passes an
  empty list [], so faithfulness and response_groundedness have nothing to
  measure against — the score would be meaningless.

● What This Codebase Does

  This is a research evaluation system for measuring how well different LLM
  models answer questions about Georgia's EV supply chain, using a knowledge
  base of 205 companies.

  ---
  The Two Phases

  Phase 1 — Response Generation (this repo)

  Offline pipeline (runs once, stored in PostgreSQL + pgvector):
  - Takes the raw company data (Normalized_kb.xlsx, 205 rows)
  - Chunks it into parent + child chunks
  - Embeds child chunks and stores them in a pgvector database (Neon PostgreSQL)
  - Builds a BM25 index for keyword search

  Runtime pipeline (runs per query):
  - Takes a question, retrieves relevant chunks via BM25 + dense vector search
  in parallel
  - Merges results, maps children back to parent chunks, reranks with a
  cross-encoder
  - Passes top-45 parent chunks as context to the LLM
  - Returns a generated answer

  Four answer pipelines being compared:

  ┌─────────────────┬────────────────────────────────────────────────────────┐
  │    Pipeline     │                     How it answers                     │
  ├─────────────────┼────────────────────────────────────────────────────────┤
  │ rag_only        │ Strict context-only — only uses retrieved chunks, no   │
  │                 │ LLM reasoning beyond them                              │
  ├─────────────────┼────────────────────────────────────────────────────────┤
  │ hybrid_rag      │ Retrieved chunks + allows LLM reasoning on top         │
  ├─────────────────┼────────────────────────────────────────────────────────┤
  │ pretrained_only │ No KB context at all — pure LLM knowledge              │
  ├─────────────────┼────────────────────────────────────────────────────────┤
  │ direct_kb       │ Skips retrieval entirely — passes all 205 raw KB rows  │
  │                 │ directly to the LLM                                    │
  └─────────────────┴────────────────────────────────────────────────────────┘

  run_baseline.py loops over 7 models × 4 pipelines × 50 questions = 1,400 LLM 
  calls, saving results as JSONL files. Retrieval runs once per question and is
  reused across all 7 models.

  ---
  Phase 2 — RAGAS Evaluation (Downloads/Comparision_Report)

  build_ragas_report.py converts the JSONL files into an Excel workbook the
  RAGAS script expects.

  evaluate_ragas_ollama.py scores every answer using a judge LLM with 4 metrics:

  ┌───────────────────────┬────────────────────────────┬────────────────────┐
  │        Metric         │      What it measures      │       Needs        │
  ├───────────────────────┼────────────────────────────┼────────────────────┤
  │ answer_accuracy       │ Is the answer correct vs   │ question + answer  │
  │                       │ golden answer?             │ + ground truth     │
  ├───────────────────────┼────────────────────────────┼────────────────────┤
  │ faithfulness          │ Did the model invent facts │ question + answer  │
  │                       │  not in the context?       │ + contexts         │
  ├───────────────────────┼────────────────────────────┼────────────────────┤
  │ response_groundedness │ How much of the answer is  │ answer + contexts  │
  │                       │ anchored in the context?   │                    │
  ├───────────────────────┼────────────────────────────┼────────────────────┤
  │                       │ Is the answer actually     │                    │
  │ answer_relevancy      │ on-topic with the          │ question + answer  │
  │                       │ question?                  │                    │
  └───────────────────────┴────────────────────────────┴────────────────────┘

  ---
  End-to-End Flow

  Normalized_kb.xlsx (205 companies)
          ↓ offline pipeline (once)
    pgvector + BM25 index
          ↓ run_baseline.py (~6-12 hrs)
    28 JSONL files (7 models × 4 pipelines, 50 questions each)
          ↓ build_ragas_report.py (seconds)
    ragas_report.xlsx
          ↓ evaluate_ragas_ollama.py (~8-10 hrs)
    ragas_report_ragas.xlsx  ← final comparison scores

  The goal is a research baseline: a table showing which LLM model + which
  pipeline combination produces the most accurate, faithful, and relevant
  answers about Georgia's EV supply chain.
