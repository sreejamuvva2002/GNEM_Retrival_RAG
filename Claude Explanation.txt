  Slide: Embedding Model — nomic-embed-text-v1.5

  - Model: nomic-ai/nomic-embed-text-v1.5, an open-source text embedding model
  from Nomic AI, loaded via the sentence-transformers library with
  trust_remote_code enabled.
  - Matryoshka Embeddings: Supports variable-length vector dimensions
  (Matryoshka Representation Learning), allowing the pipeline to trade off
  between retrieval accuracy and storage/compute cost.
  - High-Dimensional Dense Vectors: Produces up to 768-dimensional dense
  vectors, stored in PostgreSQL using the pgvector extension for efficient
  cosine similarity search.
  - Dual Role: Used in both the offline indexing pipeline (to embed document
  chunks at index time) and the runtime retrieval pipeline (to embed incoming
  queries for dense vector lookup).
  - Runs Locally / On-Prem: The model is downloaded and executed locally — no
  external API calls required — making it suitable for air-gapped or
  cost-sensitive deployments.

● Our reranker uses a Cross-Encoder (cross-encoder/ms-marco-MiniLM-L12-v2).
  Here's how the score works in simple words:

  No explicit formula in our code — the score comes directly from the model's
  predict() call. Internally, the cross-encoder:

  1. Takes the (query, chunk text) pair and feeds both together into a
  BERT-style transformer.
  2. The model outputs a single logit score (a raw number) representing how
  relevant the chunk is to the query.
  3. Higher score = more relevant. Chunks are then sorted by this score and
  top-K are kept.

  So unlike cosine similarity (which has a clear formula), the relevance score
  here is a learned neural score — the model was trained on MS MARCO passage
  ranking data to directly predict relevance, not derived from a hand-crafted
  formula.

● Here is the full explanation with slide points:

  ---
  How BM25 works in our pipeline:

  1. Index built at startup (in-memory)
  All child chunks are loaded from PostgreSQL, converted to structured text
  using field names + values (e.g., chunk_type: station metadata: ...),
  tokenized, and fed into BM25Okapi — built once, reused for every query.

  2. Custom domain-aware tokenizer
  Not a simple word split. It handles:
  - Hyphenated terms: Hyundai-Kia → [hyundai-kia, hyundai, kia]
  - Slash patterns: Tier 1/2 → [1/2, 1, 2]
  - Possessives: company's → company

  3. BM25 Okapi formula (include this in slides):

  $$\text{score}(q, d) = \sum_{t \in q} IDF(t) \cdot \frac{f(t,d) \cdot (k_1 +
  1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})}$$

  Where:
  - f(t,d) = term frequency in document
  - IDF(t) = how rare the term is across all chunks
  - |d| = document length, avgdl = average doc length
  - k1, b = tuning constants (defaults: k1=1.5, b=0.75)

  4. Only positive scores returned
  Line 123 filters out chunks with score ≤ 0 — meaning chunks with zero term
  overlap with the query are discarded entirely.

  5. No persistence — BM25 index lives in memory, rebuilt on every cold start
  from the database.

  ---
  For your slides, the key points are: custom tokenizer, BM25 Okapi formula,
  in-memory index from PostgreSQL, scores-only-positive filter, top 250
  returned.

● This is an Excel limitation warning, not a code bug.

  What it means:

  Excel has a hard limit of 32,767 characters per cell. When the code writes the
   retrieved parent chunks (45 chunks worth of text) into a single Excel cell,
  the combined text exceeds that limit — in this case 71,064 characters — so
  Excel silently cuts it off at 32,767.

  Which column is causing it:

  The retrieved_parent_chunks_after_reranking column — it contains all 45
  reranked parent chunks concatenated into one cell. That's a lot of text.

  What data is lost:

  Only the Excel display is truncated. The actual retrieval and answer
  generation in the pipeline ran on the full data — nothing was lost in
  processing. It only affects what you can read in the spreadsheet.

  How to fix it if needed:

  Either split the chunks across multiple rows/columns, or save that column as a
   separate JSON/text file instead of putting it in Excel. But if you only use
  the Excel for reviewing answers and not the raw chunks, it doesn't matter.
